# Physical trial withdrawn — uncontrolled oscillation reported

Do not use the prior software passes or KEYFRAME_LAB button instructions as
clearance to repeat this trial. The user powered the robot off after reporting
violent oscillation of every motor. Root cause is not established. Retrieve the
incident logs without enabling motor power before choosing a corrective change.

## Investigation update: immediate startup stop reproduced

After the operator powered the Pi back on and authorized investigation, no motor
stack was running. The D-pad launcher was disabled and stopped to prevent an
unintended later launch. No motor command or hardware activation was performed.
Original evidence was copied on the Pi to `/home/pi/keyframe-incident-evidence`
and locally to `C:/Users/tundt/Desktop/quadmorph-lab-recordings/keyframe-incident-20260911/`.
No production controller change has been deployed as part of this investigation.

**The first-cycle timing bug is established in code and reproduced in the actual
controller plugin with fake interfaces.** The Pi's controller-manager 4.25.0
[activation/update implementation](https://github.com/ros-controls/ros2_control/blob/4.25.0/controller_manager/src/controller_manager.cpp#L2366-L2404)
initializes the previous update timestamp to the current timestamp on the first
update, then passes their difference (zero) to the controller. The keyframe
adapter forwards this period to `Controller::step`, whose validity test requires
`dt > 0`. The core enters STOPPED; the adapter latches `estop_active_`, returns
ROS update OK, and commands kp=0/kd=1 on all joints indefinitely. Subsequent leg
commands cannot clear that latch. This defect exactly explains a successful X
activation with no entry motion. The initial tests supplied 1/520 seconds on
their first call; running those fixtures natively on the Pi did not exercise the
real manager's first-cycle timing semantics.

Reproduction: build the keyframe_controller_test fixture, set
`KEYFRAME_REPRO_ZERO_PERIOD=1`, and run its CTest. Against the installed local
plugin it reported: first period zero, STOPPED, all twelve kp=0/kd=1, later leg
request ignored. Runtime source was unchanged. This mode deliberately reproduces
the known defect; a passing reproduction is not evidence that it is fixed.
Log: local evidence `keyframe-zero-period-repro.log`.

Recovered evidence supports this sequence:

- Launch log: activation successful at 1789183672.30, then front-left request at
  1789183676.63 and front-right at 1789183680.04. X reached the intended controller.
- Every recovered status message (40 messages, timestamps 1789183672.399 through
  1789183674.355) reports phase 7/STOPPED and authority false. All stored position
  fields remain zero, matching a stop before a successful trajectory update.
- Joint-state effort is a **command-derived estimate**, not measured motor torque
  (see hardware `copy_actuator_states` formula). Its ratio `-effort/velocity` is
  exactly 0.2 before activation and 1.0 after activation across recovered samples,
  corroborating the change to active damping. It does not measure torque stability.

The original MCAP SHA256 is
`195204be929cb470bec48df52c2223d08d0aa6f28d21c9efb41b2276291534bc`.
Abrupt power loss left a zero-filled hole around byte 4071459 and an incomplete
tail. Ordinary sequential decoding stopped before X. `recover_chunks.py` salvaged
nine complete, structurally valid uncompressed chunks into a separate file;
chunk CRCs were not present. No original bytes were modified. The recovered
messages extend only through 1789183674.374, before the later wheel requests and
reported violent oscillation. Missing data must not be interpreted as zero motion.

**Oscillation cause remains partly unresolved.** Energized kd=1 braking after an
immediate fault is the leading control-path explanation, but the recovered data
does not cover the physical oscillation itself. Do not attribute it conclusively
to touching the wheel, velocity noise, scheduling, or a specific driver defect.
The previous-boot journal shows unrelated GUI/voice services repeatedly failing
and restarting; this is background load, not proof of causation. No matching
kernel OOM, undervoltage or lockup report was found in the saved journal. The
reason SSH became unreachable is also unconfirmed.

Before another physical release: correctly bootstrap the first zero-length
interval while preserving later timing-fault checks; add a real manager-to-plugin
activation test; report explicit fault reasons; and redesign/validate fault output
behavior so a hidden startup fault does not leave unverified braking on every
motor. Do not simply change kd and retry. Physical motor response, command/feedback
delay, and the stop path need staged validation before another all-joint trial.

## Concrete code findings, not a root-cause claim

`src/keyframe_controller.cpp` calls `brake()` after successful activation and on
latched stop. It zeros position, velocity, effort and kp, but sets kd=1 on every
motor. Its activation-error handler also writes kd=1. The inherited
`NeuralController::on_deactivate` retains that damping. Normal keyframe gains
are proximal kp=5/kd=0.25 and hub kp=0/kd=0.35. This is energized closed-loop
braking, not motor disable; stable physical behavior cannot be inferred from
the name `brake` or the fact that commanded velocity is zero.

The keyframe plugin test explicitly expects kd=1 in stop. Its fake plant follows
position/velocity commands directly and does not model current-loop response,
feedback delay, velocity noise, or braking stability. Simulation/ABI tests also
do not validate the physical motor driver's stop dynamics. Passing those checks
was insufficient evidence for the readiness statement given before this trial.

Possible lines of investigation include activation failure or an immediate
latched fault leaving active damping, motor feedback/control-loop instability,
and timing/scheduling behavior during activation. None is confirmed. Do not
blindly lower gains, widen sensor limits, disable calibration, or repeat motion
to obtain a diagnosis.
